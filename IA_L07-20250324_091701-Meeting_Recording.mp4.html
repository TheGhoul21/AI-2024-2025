Search and Game Playing

The Minimax Algorithm

Core Idea and Game Tree Example

The Minimax algorithm is used in two-player, zero-sum games. The two players are typically called Max and Min. Max aims to maximize the utility, while Min aims to minimize it. The game is represented as a tree, where nodes represent game states and edges represent moves. The algorithm works by propagating utility values from the leaf nodes (terminal states) up the tree.

  • Max Nodes: Choose the move that maximizes the utility.

  • Min Nodes: Choose the move that minimizes the utility (assuming perfect play by the opponent).

Example: The lecture uses the example of Pacman and a ghost, where Pacman (Max) tries to maximize its score by eating pellets, and the ghost (Min) tries to minimize Pacman’s score. Another example shown is the Tic-Tac-Toe game.

Formal Definition (Recursive)

The Minimax value of a node can be defined recursively:

Let \(S\) be a node in the game tree. The Minimax value, denoted by \(\text{Minimax}(S)\), is defined as follows:

  • If \(S\) is a terminal node, then \(\text{Minimax}(S) = \text{Utility}(S, \text{Max})\), where \(\text{Utility}(S, \text{Max})\) is the utility of the state \(S\) for player Max.

  • If it’s Max’s turn to move at node \(S\), then \[\text{Minimax}(S) = \max_{a \in \text{Actions}(S)} \text{Minimax}(\text{Result}(S, a))\] where \(\text{Actions}(S)\) is the set of possible actions at state \(S\), and \(\text{Result}(S, a)\) is the state resulting from taking action \(a\) in state \(S\).

  • If it’s Min’s turn to move at node \(S\), then \[\text{Minimax}(S) = \min_{a \in \text{Actions}(S)} \text{Minimax}(\text{Result}(S, a))\]

Implementation (Pseudocode and Book Version)

The lecture presents two versions of the Minimax algorithm implementation.

Version 1 (Pseudocode):

function Minimax-Decision(state) returns an action
  return argmax_{a in Actions(state)} Minimax-Value(Result(state, a))

function Minimax-Value(state) returns a utility value
  if Terminal-Test(state) then return Utility(state)
  if To-Move(state) = Max then return max_{a in Actions(state)} Minimax-Value(Result(state, a))
  else return min_{a in Actions(state)} Minimax-Value(Result(state, a))

Version 2 (Book Version - Figure 6.3): This version is more detailed and uses three functions: ‘Minimax-Search’, ‘Max-Value’, and ‘Min-Value’.

function Minimax-Search(game, state) returns an action
  player = game.To-Move(state)
  value, move = Max-Value(game, state)
  return move

function Max-Value(game, state) returns a (utility, move) pair
  if game.Is-Terminal(state) then return game.Utility(state, player), null
  v = -Infinity
  move = -Infinity // Note: Initialization to -Infinity might be unnecessary
  for each a in game.Actions(state) do
    v2, a2 = Min-Value(game, game.Result(state, a))
    if v2 > v then
      v = v2
      move = a
  return v, move

function Min-Value(game, state) returns a (utility, move) pair
  if game.Is-Terminal(state) then return game.Utility(state, player), null
  v = Infinity
  move = -Infinity // Note: Initialization to -Infinity might be unnecessary
  for each a in game.Actions(state) do
    v2, a2 = Max-Value(game, game.Result(state, a))
    if v2 < v then
      v = v2
      move = a
  return v, move

The book version, while more verbose, is closer to executable code. It explicitly returns both the utility and the best move found. The pseudocode version is more concise and focuses on the core logic.

Alpha-Beta Pruning

Efficiency Issues with Minimax

The Minimax algorithm has a time complexity of \(O(b^m)\), where \(b\) is the branching factor (number of possible moves at each state) and \(m\) is the maximum depth of the game tree. This makes it computationally infeasible for games like chess, where \(b \approx 35\) and \(m \approx 100\) (considering 50 moves per player). Such exponential complexity severely limits the depth of the search tree that can be explored in a reasonable amount of time.

Pruning Concept and Example

Alpha-Beta pruning is a technique to improve the efficiency of Minimax by avoiding the exploration of parts of the game tree that are guaranteed not to affect the final decision. The core idea is to maintain two values:

  • \(\alpha\): The best (highest) value found so far for Max along the path. This represents the minimum score that Max is guaranteed to achieve.

  • \(\beta\): The best (lowest) value found so far for Min along the path. This represents the maximum score that Min can achieve (or, equivalently, the maximum score that Max can be limited to).

The lecture provides a detailed example demonstrating how Alpha-Beta pruning works. The key idea is that if a Min node finds a value less than or equal to \(\alpha\), the rest of its children can be pruned because Max will never choose that branch (since Max already has a better option with value \(\alpha\)). Similarly, if a Max node finds a value greater than or equal to \(\beta\), the rest of its children can be pruned (since Min already has a better option with value \(\beta\)).

Formalizing Alpha-Beta Pruning

The general idea of Alpha-Beta pruning is as follows:

  • Maintain \(\alpha\) (best for Max) and \(\beta\) (best for Min) values along the path from the root to the current node. These values are updated as the search progresses.

  • At a Min node \(n\), if the value \(v\) of \(n\) (after evaluating a child) is less than or equal to \(\alpha\) (considering all Max ancestors), prune the remaining children of \(n\). This is because Max already has a guaranteed score of at least \(\alpha\), and Min is trying to minimize the score, so any further exploration of \(n\)’s children will only lead to values less than or equal to \(v\), which are worse for Max.

  • At a Max node \(n\), if the value \(v\) of \(n\) (after evaluating a child) is greater than or equal to \(\beta\) (considering all Min ancestors), prune the remaining children of \(n\). This is because Min already has a guaranteed score of at most \(\beta\), and Max is trying to maximize the score, so any further exploration of \(n\)’s children will only lead to values greater than or equal to \(v\), which are worse for Min.

Implementation and Efficiency Gains

The Alpha-Beta pruning algorithm is a modification of the Minimax algorithm. The ‘Max-Value’ and ‘Min-Value’ functions are updated to take \(\alpha\) and \(\beta\) as parameters, and the pruning logic is incorporated.

function Alpha-Beta-Search(game, state) returns an action
  player = game.To-Move(state)
  value, move = Max-Value(game, state, -Infinity, Infinity)
  return move

function Max-Value(game, state, alpha, beta) returns a (utility, move) pair
  if game.Is-Terminal(state) then return game.Utility(state, player), null
  v = -Infinity
  move = null
  for each a in game.Actions(state) do
    v2, a2 = Min-Value(game, game.Result(state, a), alpha, beta)
    if v2 > v then
      v = v2
      move = a
      alpha = max(alpha, v)
    if v >= beta then return v, move // Pruning
  return v, move

function Min-Value(game, state, alpha, beta) returns a (utility, move) pair
  if game.Is-Terminal(state) then return game.Utility(state, player), null
  v = Infinity
  move = null
  for each a in game.Actions(state) do
    v2, a2 = Max-Value(game, game.Result(state, a), alpha, beta)
    if v2 < v then
      v = v2
      move = a
      beta = min(beta, v)
    if v <= alpha then return v, move // Pruning
  return v, move

Alpha-Beta pruning does *not* change the Minimax value; it only improves efficiency. It returns the same move as Minimax would, but it often does so much faster. With perfect ordering of the children (i.e., the best moves for each player are considered first), the time complexity can be reduced to \(O(b^{m/2})\), effectively doubling the searchable depth. However, even with Alpha-Beta pruning, chess remains computationally challenging, as \(O(35^{50})\) is still a very large number. In practice, the actual performance of Alpha-Beta pruning depends on the order in which the children are evaluated. Heuristics are often used to try to achieve near-optimal ordering.

Applications in Games

Historical Context: Samuel’s Checkers Program

Arthur Samuel’s checkers program (1950s) was an early example of AI using game playing. It used Minimax, Alpha-Beta pruning, and some learning techniques. Samuel’s program was notable for its ability to learn from its mistakes and improve its play over time. This was achieved through a combination of rote learning (memorizing board positions and their values) and generalization (using a scoring function to evaluate new positions).

Deep Blue, Kasparov, and AI

Deep Blue’s victory over Garry Kasparov in chess (1997) was a significant milestone in AI. Deep Blue used Alpha-Beta Minimax search with a static evaluation function, along with extensive hardware optimization. The evaluation function was handcrafted by chess experts and assigned numerical values to various features of a chess position (e.g., material balance, pawn structure, king safety). There was debate at the time about whether this constituted "true" AI or just brute force, as Deep Blue relied heavily on its ability to search a vast number of positions very quickly.

AlphaGo, AlphaGo Zero, and Monte Carlo Tree Search

AlphaGo and AlphaGo Zero represent more recent advancements in AI game playing. AlphaGo used a combination of deep neural networks (trained through supervised learning from expert games and reinforcement learning from self-play) and Monte Carlo Tree Search (MCTS). AlphaGo Zero learned to play Go by playing against itself, without any human knowledge, relying solely on reinforcement learning. MCTS is often preferred over Alpha-Beta pruning for efficiency in games with large branching factors, like Go. MCTS works by selectively expanding the game tree, guided by simulations, and gradually converging towards the optimal moves.

Even with techniques like Alpha-Beta pruning and MCTS, pure search has limitations. Heuristic evaluation functions and learning techniques are often necessary to achieve high performance in complex games. For games like chess and Go, it’s impossible to search the entire game tree, so the agent must rely on an evaluation function to estimate the value of non-terminal positions. The quality of this evaluation function is crucial to the agent’s performance. Learning techniques, such as those used in AlphaGo and AlphaGo Zero, allow the agent to improve its evaluation function and its search strategy over time.

Knowledge-Based Agents: Foundations

Introduction and Motivation

Human Knowledge and Reasoning

Humans possess a vast amount of knowledge about the world and use it to reason, make decisions, and solve problems. For example, we know that if it rains, we should take an umbrella. We also know that umbrellas provide protection from rain, and that getting wet in the rain can be unpleasant or lead to illness. This interconnected web of knowledge allows us to make informed choices.

Limitations of Previous Agents

The problem-solving agents discussed previously (search-based agents, like those using A* or Minimax) have limited knowledge. They can solve specific, well-defined problems (e.g., finding a path in a graph, playing chess), but they lack general knowledge about the world (e.g., weather, distances, object properties). They cannot answer questions outside their narrow domain of expertise or adapt to novel situations that require common sense reasoning. For instance, a chess-playing agent doesn’t understand the concept of "tomorrow" or "weather."

Knowledge Representation and Knowledge Bases

Sentences and Formal Languages

Knowledge-based agents store knowledge explicitly in a knowledge base (KB). The knowledge base is a set of sentences expressed in a formal language. A formal language has a well-defined syntax (rules for forming valid sentences) and semantics (rules for determining the meaning of sentences). Historically, this language has often been first-order predicate calculus (logic), but other representations are possible, including semantic networks, frames, and, more recently, natural language (with the aid of large language models).

Axioms and Derived Knowledge

The knowledge base contains:

  • Axioms: Sentences that are given as true initially (provided by the system designer or learned through some initial training process). These are the foundational facts and rules that the agent starts with.

  • Derived Knowledge: Sentences that are inferred from the axioms and other derived sentences using an inference engine. This is the knowledge that the agent deduces based on its initial knowledge and reasoning capabilities.

Inference Engines

Tell and Ask Functions

Knowledge-based agents interact with the knowledge base through two primary functions:

  • Tell: Adds new sentences to the knowledge base. This is how the agent learns new facts or rules, either from external input (e.g., a user telling it something) or from its own perception and learning mechanisms.

  • Ask: Queries the knowledge base, potentially requiring inference. This is how the agent retrieves information and makes decisions. The query might be a simple question about a known fact, or it might require the agent to deduce an answer based on its existing knowledge.

Deriving Consequences

The inference engine is responsible for deriving logical consequences from the knowledge base. This is what distinguishes a knowledge base from a simple database. A database typically stores facts and retrieves them directly. A knowledge base, on the other hand, can infer new facts that are not explicitly stored but are logically implied by the existing knowledge. The ‘Ask’ function can return not only explicitly stored facts but also inferred facts.

Example: If the KB knows that \(A = 0\), and it is asked if \(A \times B = 0\), it can infer the answer (yes) even if it’s not explicitly stored, because it has knowledge about the properties of multiplication. Similarly, if it knows \(x + y = 2\) and \(x = 1\), it can infer that \(y = 1\) using basic algebraic principles. More complex inferences are possible, involving multiple steps of reasoning and combining different pieces of knowledge.

Agent Architecture

Generic Knowledge-Based Agent Code

A generic knowledge-based agent can be described with the following pseudocode:

function KB-Agent(percept) returns an action
  persistent: KB, a knowledge base
              t, a counter, initially 0

  Tell(KB, Make-Percept-Sentence(percept, t))
  action = Ask(KB, Make-Action-Query(t))
  Tell(KB, Make-Action-Sentence(action, t))
  t = t + 1
  return action

The "intelligence" of this agent resides in the knowledge base (the ‘KB’) and the ‘Ask’ function’s implementation (the inference engine). The agent’s behavior is determined by what it knows and how it can reason with that knowledge. The ‘Make-Percept-Sentence’, ‘Make-Action-Query’, and ‘Make-Action-Sentence’ functions are responsible for translating between the agent’s internal representation and the external world (percepts and actions).

Declarative vs. Procedural Approaches

Knowledge-based agents represent a declarative approach, where knowledge is represented explicitly as sentences in a formal language. This contrasts with a procedural approach, where knowledge is encoded implicitly within the program’s code (e.g., the specific steps of the Minimax algorithm or the weights in a neural network). Historically, there were debates about which approach was better for building intelligent systems, but it’s now understood that both have their strengths and weaknesses, and a combination of both is often beneficial. Declarative approaches are often more flexible and easier to understand and modify, while procedural approaches can be more efficient for specific tasks.

Knowledge Level

Knowledge-based agents allow reasoning at the knowledge level, meaning we can discuss what the agent *knows* rather than just how it’s implemented. We can analyze the agent’s behavior in terms of its beliefs, goals, and the inferences it can make, independent of the specific algorithms or data structures used to implement the knowledge base and inference engine. This provides a higher level of abstraction for understanding and designing intelligent systems.

The Wumpus World: A Case Study

Environment Definition (PEAS)

Performance Measure

The agent’s performance is measured by a score that reflects its success in achieving its goals and avoiding dangers:

  • +1000 for finding the gold, returning to the starting square (1,1), and climbing out of the cave.

  • -1000 for falling into a pit or being eaten by the Wumpus (game over).

  • -1 for each action taken (to encourage efficiency).

  • -10 for using the arrow (to encourage using it strategically).

Environment Structure

The Wumpus World is a 4x4 grid of rooms (a cave) with the following characteristics:

  • Grid Size: 4x4, totaling 16 rooms.

  • Agent Starting Position: The agent always starts in the square (1,1), facing east.

  • Wumpus and Pit Locations: The locations of the Wumpus and pits are randomly chosen at the beginning of each game, with the following constraints:

    • The Wumpus and pits cannot be in the starting square (1,1).

    • There is exactly one Wumpus, placed uniformly randomly in one of the remaining 15 squares.

    • Each room (except (1,1)) has an independent probability of 0.2 of containing a pit. This means there could be anywhere from zero to 15 pits.

  • Gold Location: There is one piece of gold, placed randomly in one of the squares.

  • Walls: The entire grid is surrounded by walls.

Actuators/Actions

The agent has the following actions available:

  • Forward: Move forward one square in the direction the agent is facing. If the agent attempts to move into a wall, it stays in the same square and receives a "bump" percept.

  • TurnLeft: Turn 90 degrees to the left (counterclockwise).

  • TurnRight: Turn 90 degrees to the right (clockwise).

  • Grab: Pick up the gold if the agent is in the same square as the gold.

  • Shoot: Fire the arrow in a straight line in the direction the agent is facing. The arrow continues until it hits the Wumpus (killing it) or a wall. The agent has only one arrow.

  • Climb: Exit the cave. This action is only successful if the agent is in the starting square (1,1).

Sensors

The agent has five sensors that provide information about its immediate surroundings:

  • Stench: Detects if the agent is in a square directly adjacent (north, south, east, or west, but not diagonally) to the Wumpus.

  • Breeze: Detects if the agent is in a square directly adjacent (north, south, east, or west) to a pit.

  • Glitter: Detects if the agent is in the same square as the gold.

  • Bump: Detects if the agent has attempted to move into a wall.

  • Scream: Detects the Wumpus’s scream when it is killed by the arrow. This scream is perceived anywhere in the cave.

"Adjacent" means directly north, south, east, or west (not diagonal).

Example Reasoning Scenario

Why Simple Search Fails

Simple search algorithms, like breadth-first search or depth-first search, are inadequate for the Wumpus World because the environment is partially observable. The agent cannot directly perceive the location of the Wumpus or pits. It only receives local sensory information (stench, breeze, glitter, bump, scream). Trying a random action (e.g., moving forward) can lead to death if the agent unknowingly moves into a square with a pit or the Wumpus. A pure search approach, without reasoning about the implications of percepts, would be extremely inefficient and dangerous.

Deductive Reasoning

The agent must use deductive reasoning, combining its percepts with its knowledge of the rules of the Wumpus World, to infer the locations of dangers and safe squares. It needs to build a model of the world and update that model as it gathers more information.

Example:

  1. The agent starts in (1,1) and perceives nothing (no stench, no breeze, no glitter). It can safely conclude that the adjacent squares (1,2) and (2,1) are safe (no Wumpus, no pit). It can then safely move to, say, (2,1).

  2. In (2,1), the agent perceives a breeze. This means there’s a pit in at least one of the adjacent squares: (2,2) or (3,1) (or both), but the agent doesn’t know which. It cannot safely move to either of those squares without more information.

  3. The agent can return to (1,1) (which it knows is safe) and then move to (1,2).

  4. In (1,2), the agent perceives a stench but no breeze. Since there’s no breeze, the agent can deduce that there is *no* pit in (2,2). This is a crucial step that requires logical reasoning, not just search. If there *were* a pit in (2,2), the agent would have perceived a breeze in (1,2). The stench indicates the Wumpus is nearby, likely in (1,3) or (2,3).

This example illustrates how the agent must use logic to combine percepts and deduce the state of the world. It cannot simply explore the search space blindly. It needs to reason about the implications of its percepts to avoid danger and find the gold.

Conclusion

This lecture introduced knowledge-based agents and the Wumpus World. Key takeaways include:

  • Knowledge-based agents store knowledge explicitly in a knowledge base, allowing for a declarative approach to AI.

  • Inference engines derive new knowledge from existing knowledge, enabling the agent to go beyond simple retrieval of facts.

  • The Wumpus World is a partially observable environment that requires reasoning and deduction, highlighting the limitations of pure search.

  • Simple search algorithms are insufficient for the Wumpus World due to the hidden dangers and the need for logical inference.

than or equal to $\alpha$, the rest of its children can be pruned
because Max will never choose that branch (since Max already has a
better option with value $\alpha$). Similarly, if a Max node finds a
value greater than or equal to $\beta$, the rest of its children can be
pruned (since Min already has a better option with value $\beta$).

### Formalizing Alpha-Beta Pruning

The general idea of Alpha-Beta pruning is as follows:

-   Maintain $\alpha$ (best for Max) and $\beta$ (best for Min) values
    along the path from the root to the current node. These values are
    updated as the search progresses.

-   At a Min node $n$, if the value $v$ of $n$ (after evaluating a
    child) is less than or equal to $\alpha$ (considering all Max
    ancestors), prune the remaining children of $n$. This is because Max
    already has a guaranteed score of at least $\alpha$, and Min is
    trying to minimize the score, so any further exploration of $n$'s
    children will only lead to values less than or equal to $v$, which
    are worse for Max.

-   At a Max node $n$, if the value $v$ of $n$ (after evaluating a
    child) is greater than or equal to $\beta$ (considering all Min
    ancestors), prune the remaining children of $n$. This is because Min
    already has a guaranteed score of at most $\beta$, and Max is trying
    to maximize the score, so any further exploration of $n$'s children
    will only lead to values greater than or equal to $v$, which are
    worse for Min.

### Implementation and Efficiency Gains

The Alpha-Beta pruning algorithm is a modification of the Minimax
algorithm. The 'Max-Value' and 'Min-Value' functions are updated to take
$\alpha$ and $\beta$ as parameters, and the pruning logic is
incorporated.

    function Alpha-Beta-Search(game, state) returns an action
      player = game.To-Move(state)
      value, move = Max-Value(game, state, -Infinity, Infinity)
      return move

    function Max-Value(game, state, alpha, beta) returns a (utility, move) pair
      if game.Is-Terminal(state) then return game.Utility(state, player), null
      v = -Infinity
      move = null
      for each a in game.Actions(state) do
        v2, a2 = Min-Value(game, game.Result(state, a), alpha, beta)
        if v2 > v then
          v = v2
          move = a
          alpha = max(alpha, v)
        if v >= beta then return v, move // Pruning
      return v, move

    function Min-Value(game, state, alpha, beta) returns a (utility, move) pair
      if game.Is-Terminal(state) then return game.Utility(state, player), null
      v = Infinity
      move = null
      for each a in game.Actions(state) do
        v2, a2 = Max-Value(game, game.Result(state, a), alpha, beta)
        if v2 < v then
          v = v2
          move = a
          beta = min(beta, v)
        if v <= alpha then return v, move // Pruning
      return v, move

Alpha-Beta pruning does \*not\* change the Minimax value; it only
improves efficiency. It returns the same move as Minimax would, but it
often does so much faster. With perfect ordering of the children (i.e.,
the best moves for each player are considered first), the time
complexity can be reduced to $O(b^{m/2})$, effectively doubling the
searchable depth. However, even with Alpha-Beta pruning, chess remains
computationally challenging, as $O(35^{50})$ is still a very large
number. In practice, the actual performance of Alpha-Beta pruning
depends on the order in which the children are evaluated. Heuristics are
often used to try to achieve near-optimal ordering.

## Applications in Games

### Historical Context: Samuel's Checkers Program

Arthur Samuel's checkers program (1950s) was an early example of AI
using game playing. It used Minimax, Alpha-Beta pruning, and some
learning techniques. Samuel's program was notable for its ability to
learn from its mistakes and improve its play over time. This was
achieved through a combination of rote learning (memorizing board
positions and their values) and generalization (using a scoring function
to evaluate new positions).

### Deep Blue, Kasparov, and AI

Deep Blue's victory over Garry Kasparov in chess (1997) was a
significant milestone in AI. Deep Blue used Alpha-Beta Minimax search
with a static evaluation function, along with extensive hardware
optimization. The evaluation function was handcrafted by chess experts
and assigned numerical values to various features of a chess position
(e.g., material balance, pawn structure, king safety). There was debate
at the time about whether this constituted \"true\" AI or just brute
force, as Deep Blue relied heavily on its ability to search a vast
number of positions very quickly.

### AlphaGo, AlphaGo Zero, and Monte Carlo Tree Search

AlphaGo and AlphaGo Zero represent more recent advancements in AI game
playing. AlphaGo used a combination of deep neural networks (trained
through supervised learning from expert games and reinforcement learning
from self-play) and Monte Carlo Tree Search (MCTS). AlphaGo Zero learned
to play Go by playing against itself, without any human knowledge,
relying solely on reinforcement learning. MCTS is often preferred over
Alpha-Beta pruning for efficiency in games with large branching factors,
like Go. MCTS works by selectively expanding the game tree, guided by
simulations, and gradually converging towards the optimal moves.

Even with techniques like Alpha-Beta pruning and MCTS, pure search has
limitations. Heuristic evaluation functions and learning techniques are
often necessary to achieve high performance in complex games. For games
like chess and Go, it's impossible to search the entire game tree, so
the agent must rely on an evaluation function to estimate the value of
non-terminal positions. The quality of this evaluation function is
crucial to the agent's performance. Learning techniques, such as those
used in AlphaGo and AlphaGo Zero, allow the agent to improve its
evaluation function and its search strategy over time.

# Knowledge-Based Agents: Foundations

## Introduction and Motivation

### Human Knowledge and Reasoning

Humans possess a vast amount of knowledge about the world and use it to
reason, make decisions, and solve problems. For example, we know that if
it rains, we should take an umbrella. We also know that umbrellas
provide protection from rain, and that getting wet in the rain can be
unpleasant or lead to illness. This interconnected web of knowledge
allows us to make informed choices.

### Limitations of Previous Agents

The problem-solving agents discussed previously (search-based agents,
like those using A\* or Minimax) have limited knowledge. They can solve
specific, well-defined problems (e.g., finding a path in a graph,
playing chess), but they lack general knowledge about the world (e.g.,
weather, distances, object properties). They cannot answer questions
outside their narrow domain of expertise or adapt to novel situations
that require common sense reasoning. For instance, a chess-playing agent
doesn't understand the concept of \"tomorrow\" or \"weather.\"

## Knowledge Representation and Knowledge Bases

### Sentences and Formal Languages

Knowledge-based agents store knowledge explicitly in a **knowledge base
(KB)**. The knowledge base is a set of **sentences** expressed in a
formal language. A formal language has a well-defined syntax (rules for
forming valid sentences) and semantics (rules for determining the
meaning of sentences). Historically, this language has often been
first-order predicate calculus (logic), but other representations are
possible, including semantic networks, frames, and, more recently,
natural language (with the aid of large language models).

### Axioms and Derived Knowledge

The knowledge base contains:

-   **Axioms**: Sentences that are given as true initially (provided by
    the system designer or learned through some initial training
    process). These are the foundational facts and rules that the agent
    starts with.

-   **Derived Knowledge**: Sentences that are inferred from the axioms
    and other derived sentences using an inference engine. This is the
    knowledge that the agent deduces based on its initial knowledge and
    reasoning capabilities.

## Inference Engines

### Tell and Ask Functions

Knowledge-based agents interact with the knowledge base through two
primary functions:

-   **Tell**: Adds new sentences to the knowledge base. This is how the
    agent learns new facts or rules, either from external input (e.g., a
    user telling it something) or from its own perception and learning
    mechanisms.

-   **Ask**: Queries the knowledge base, potentially requiring
    inference. This is how the agent retrieves information and makes
    decisions. The query might be a simple question about a known fact,
    or it might require the agent to deduce an answer based on its
    existing knowledge.

### Deriving Consequences

The inference engine is responsible for deriving logical consequences
from the knowledge base. This is what distinguishes a knowledge base
from a simple database. A database typically stores facts and retrieves
them directly. A knowledge base, on the other hand, can infer new facts
that are not explicitly stored but are logically implied by the existing
knowledge. The 'Ask' function can return not only explicitly stored
facts but also inferred facts.

*Example:* If the KB knows that $A = 0$, and it is asked if
$A \times B = 0$, it can infer the answer (yes) even if it's not
explicitly stored, because it has knowledge about the properties of
multiplication. Similarly, if it knows $x + y = 2$ and $x = 1$, it can
infer that $y = 1$ using basic algebraic principles. More complex
inferences are possible, involving multiple steps of reasoning and
combining different pieces of knowledge.

## Agent Architecture

### Generic Knowledge-Based Agent Code

A generic knowledge-based agent can be described with the following
pseudocode:

::: tcolorbox
    function KB-Agent(percept) returns an action
      persistent: KB, a knowledge base
                  t, a counter, initially 0

      Tell(KB, Make-Percept-Sentence(percept, t))
      action = Ask(KB, Make-Action-Query(t))
      Tell(KB, Make-Action-Sentence(action, t))
      t = t + 1
      return action
:::

The \"intelligence\" of this agent resides in the knowledge base (the
'KB') and the 'Ask' function's implementation (the inference engine).
The agent's behavior is determined by what it knows and how it can
reason with that knowledge. The 'Make-Percept-Sentence',
'Make-Action-Query', and 'Make-Action-Sentence' functions are
responsible for translating between the agent's internal representation
and the external world (percepts and actions).

### Declarative vs. Procedural Approaches

Knowledge-based agents represent a **declarative** approach, where
knowledge is represented explicitly as sentences in a formal language.
This contrasts with a **procedural** approach, where knowledge is
encoded implicitly within the program's code (e.g., the specific steps
of the Minimax algorithm or the weights in a neural network).
Historically, there were debates about which approach was better for
building intelligent systems, but it's now understood that both have
their strengths and weaknesses, and a combination of both is often
beneficial. Declarative approaches are often more flexible and easier to
understand and modify, while procedural approaches can be more efficient
for specific tasks.

### Knowledge Level

Knowledge-based agents allow reasoning at the **knowledge level**,
meaning we can discuss what the agent \*knows\* rather than just how
it's implemented. We can analyze the agent's behavior in terms of its
beliefs, goals, and the inferences it can make, independent of the
specific algorithms or data structures used to implement the knowledge
base and inference engine. This provides a higher level of abstraction
for understanding and designing intelligent systems.

# The Wumpus World: A Case Study

## Environment Definition (PEAS)

### Performance Measure

The agent's performance is measured by a score that reflects its success
in achieving its goals and avoiding dangers:

-   +1000 for finding the gold, returning to the starting square (1,1),
    and climbing out of the cave.

-   -1000 for falling into a pit or being eaten by the Wumpus (game
    over).

-   -1 for each action taken (to encourage efficiency).

-   -10 for using the arrow (to encourage using it strategically).

### Environment Structure

The Wumpus World is a 4x4 grid of rooms (a cave) with the following
characteristics:

-   **Grid Size:** 4x4, totaling 16 rooms.

-   **Agent Starting Position:** The agent always starts in the square
    (1,1), facing east.

-   **Wumpus and Pit Locations:** The locations of the Wumpus and pits
    are randomly chosen at the beginning of each game, with the
    following constraints:

    -   The Wumpus and pits cannot be in the starting square (1,1).

    -   There is exactly one Wumpus, placed uniformly randomly in one of
        the remaining 15 squares.

    -   Each room (except (1,1)) has an independent probability of 0.2
        of containing a pit. This means there could be anywhere from
        zero to 15 pits.

-   **Gold Location:** There is one piece of gold, placed randomly in
    one of the squares.

-   **Walls:** The entire grid is surrounded by walls.

### Actuators/Actions

The agent has the following actions available:

-   `Forward`: Move forward one square in the direction the agent is
    facing. If the agent attempts to move into a wall, it stays in the
    same square and receives a \"bump\" percept.

-   `TurnLeft`: Turn 90 degrees to the left (counterclockwise).

-   `TurnRight`: Turn 90 degrees to the right (clockwise).

-   `Grab`: Pick up the gold if the agent is in the same square as the
    gold.

-   `Shoot`: Fire the arrow in a straight line in the direction the
    agent is facing. The arrow continues until it hits the Wumpus
    (killing it) or a wall. The agent has only one arrow.

-   `Climb`: Exit the cave. This action is only successful if the agent
    is in the starting square (1,1).

### Sensors

The agent has five sensors that provide information about its immediate
surroundings:

-   `Stench`: Detects if the agent is in a square directly adjacent
    (north, south, east, or west, but not diagonally) to the Wumpus.

-   `Breeze`: Detects if the agent is in a square directly adjacent
    (north, south, east, or west) to a pit.

-   `Glitter`: Detects if the agent is in the same square as the gold.

-   `Bump`: Detects if the agent has attempted to move into a wall.

-   `Scream`: Detects the Wumpus's scream when it is killed by the
    arrow. This scream is perceived anywhere in the cave.

\"Adjacent\" means directly north, south, east, or west (not diagonal).

## Example Reasoning Scenario

### Why Simple Search Fails

Simple search algorithms, like breadth-first search or depth-first
search, are inadequate for the Wumpus World because the environment is
*partially observable*. The agent cannot directly perceive the location
of the Wumpus or pits. It only receives local sensory information
(stench, breeze, glitter, bump, scream). Trying a random action (e.g.,
moving forward) can lead to death if the agent unknowingly moves into a
square with a pit or the Wumpus. A pure search approach, without
reasoning about the implications of percepts, would be extremely
inefficient and dangerous.

### Deductive Reasoning

The agent must use deductive reasoning, combining its percepts with its
knowledge of the rules of the Wumpus World, to infer the locations of
dangers and safe squares. It needs to build a model of the world and
update that model as it gathers more information.

*Example:*

1.  The agent starts in (1,1) and perceives nothing (no stench, no
    breeze, no glitter). It can safely conclude that the adjacent
    squares (1,2) and (2,1) are safe (no Wumpus, no pit). It can then
    safely move to, say, (2,1).

2.  In (2,1), the agent perceives a breeze. This means there's a pit in
    at least one of the adjacent squares: (2,2) or (3,1) (or both), but
    the agent doesn't know which. It cannot safely move to either of
    those squares without more information.

3.  The agent can return to (1,1) (which it knows is safe) and then move
    to (1,2).

4.  In (1,2), the agent perceives a stench but no breeze. Since there's
    no breeze, the agent can deduce that there is \*no\* pit in (2,2).
    This is a crucial step that requires logical reasoning, not just
    search. If there \*were\* a pit in (2,2), the agent would have
    perceived a breeze in (1,2). The stench indicates the Wumpus is
    nearby, likely in (1,3) or (2,3).

This example illustrates how the agent must use logic to combine
percepts and deduce the state of the world. It cannot simply explore the
search space blindly. It needs to reason about the implications of its
percepts to avoid danger and find the gold.
